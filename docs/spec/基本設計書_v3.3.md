## 1. はじめに

### 1.1 本書の目的

本書は、アーティスト同士の関連性をネットワークグラフで可視化し、音楽の発見（ディグ）体験を提供するモバイルアプリケーション「DIGGR」（コードネーム）の基本設計を定義する。機能要件、システム構成、データモデル、API 設計、収益モデル、非機能要件を対象とし、実装着手の判断材料となる粒度で記述する。

画面レベルの詳細は「DIGGR 画面設計書」、技術の比較検討と採用根拠は「DIGGR 技術選定書」を参照。

### 1.2 スコープ

| 区分 | 内容 |
| --- | --- |
| 対象プラットフォーム | iOS（App Store）、Android（Google Play）のネイティブアプリ |
| 対象外 | Web 版アプリケーション（実装しない。LP と法務ページのみ静的サイトで用意） |
| 対象リリース | MVP（v1.0）を主対象とし、v1.1 以降は §11 ロードマップで方向性のみ定義 |

### 1.3 用語定義

| 用語 | 定義 |
| --- | --- |
| ディグ | 未知のアーティストを掘り当てて発見する行為。本アプリの中核体験 |
| シードアーティスト | ユーザーが検索の起点として指定するアーティスト、グラフの中心ノード |
| 関連アーティスト | シードに対する類似度上位のアーティスト、グラフの子ノード |
| ノード | グラフ上の 1 アーティストを表す円形の描画要素 |
| エッジ | ノード間の関連を表す線、太さで類似度を表現する |
| 解放件数 | 1 グラフあたりに描画される関連アーティストの上限件数（無料 30 / 有料 100） |
| マップ | 1 回の生成で確定するノード集合。履歴・ブックマーク・引き直しの単位 |

## 2. システム概要

### 2.1 コンセプト

「聴いたことのないアーティスト」に最短 3 タップで出会わせる。検索窓に好きなアーティストを 1 つ入れるだけで、関連アーティストが放射状のポイントとして立ち上がり、ノードをタップすれば関係性を読み、気に入ったものを普段使っている音楽アプリでフル尺で聴かせる——ネットワークグラフの Every Noise at Once の網羅性・情報密度を、モバイルの一手操作に最適化して再構成する。

**DIGGR は「聴かせようとしない」**。音を鳴らすのは既存の音楽アプリの仕事であり、DIGGR が担うのは **その手前——どれを聴くか決めるための地図** である。役割を絞ることで、どの通信サービスの契約者でも同じ体験を得られ、規約上の制約からも自由になる（§3.5）。

したがって設計の焦点は、**聴かせる前に当てを付けさせる情報を地図の中に置くこと** に集中する。ノードの大きさ（類似度）、エッジの種別（どう関連するか）、ジャンル色、閲覧済みチェック（FR-31）——これらはすべてこの一点のためにある。

### 2.2 ターゲットユーザー

- **コアターゲット**\: サブスクで音楽を聴き飽きたヘビーリスナー。自分で掘る行為そのものを楽しめる層 18〜34 歳の
- **サブターゲット**\: DJ・選曲家・プレイリスト制作者など、隣接ジャンルを短時間で俯瞰したい実務層

### 2.3 提供価値

既存のレコメンドが「次の 1 曲」を差し出すのに対し、DIGGR は **音楽地図そのもの** を渡す。ユーザーは推薦を受け取るのではなく、自分の意志で地図を辿ることの能力性を持ち、滞在時間とダイバーシティを生み、課金・広告の両方の土台になる。

## 3. 前提条件とライセンス方針

### 3.1 設計原則: 申請・許諾を最小化する

本システムは、**第三者への利用申請・審査・個別契約に中核機能を依存させないこと** を設計上の原則とする。データ・描画・課金・広告のすべては、この原則を満たす。

### 3.1.1 原則から導かれる帰結

1. **データは「借りる」のではなく「持つ」**。CC0（パブリックドメイン）で公開されているデータをそのまま取得し、自社の基盤に取り込んで運用する
2. **ストリーミング各社の API には依存しない**。音を鳴らすアプリでの露出・アプリ内課金を制限する規約と両立しない
3. **無料枠・審査待ちの API に事業の生死を乗せない**。依存する場合は必ず縮退経路を用意する

### 3.1.2 Apple Music Feed の位置づけ

v2.1〜v2.4 では、アプリ内 30 秒プレビュー（旧 FR-06）のために **iTunes Search API を原則の例外** として採用していた。v3.0 でこの例外を取り下げる代わりに、**Apple Music Feed をデータ強化の層として採用する**。**v3.1 時点で Apple Developer Program への加入が確定しているため、採用は確定事項として扱う**。

| 観点 | v2.4（iTunes Search API） | v3.0（Apple Music Feed） |
| --- | --- | --- |
| 用途 | 試聴レビューの取得 | **月次パイプラインでのカタログメタデータ取得** |
| 前提となる手続き | Apple Services Performance Partner Program の登録審査 | **Apple Developer Program への加入**（iOS 配信のためにどちらか必要） |
| 審査の有無 | あり（パートナー登録の可否判定） | **なし**。加入後に Media ID を自分で構成して有効化する |
| 実行時に頼る外部 API | あり（ユーザータップのたび） | **なし**。月次バッチだけが触れる |
| 常駐ワーカー | 必要（18 秒/曲のポーリング） | **不要** |
| 中核機能への影響 | 失うと聴く手段が消える | **失っても中核は成立する**（下記） |

**原則の再定義**\: この原則は、外部に一切依存しないことではなく、**「中核機能」を第三者の個別審査・交渉に人質に取らせないこと** である。Apple Developer Program は、**iOS でリリースする以上どのみち加入が前提条件** であるため、そのために新たな審査を受けるわけではない。したがって **追加の関門にはならない**。

**それでもこれは依存であるから、層を分けて小さく縛る**。Apple Music Feed から得るものの **大半は強化（enrichment）** であるが、原点ではない。**ただし FR-01b を有効化すると、一部が原点に入る**（下表 3 行目）。

| 層 | 出所 | Apple が失ったとき |
| --- | --- | --- |
| **原点**\: アーティスト実体・類似度 5 信号・ジャンル階層の骨格 | CC0 4 ソース | **影響なし** |
| 強化: 人気度、Apple Music のアーティスト ID、**別名（多言語表記）**、ジャンルの補完、リリース年の補完 | Apple Music Feed | 取得済み分は使い続ける後に CC0 由来の代替値へフォールバック |
| **一部原点**\: **Apple のみに存在するアーティストの検索（FR-01b）** | **Apple Music Feed** | **そのアーティストが検索から消える**（下記） |

つまり **Apple が失っても地図は消えない**。失うものは並び順の精度、リンクのカバレッジと**別名による検索の当たりやすさ**である。**設計の骨格は CC0 の側に置いたままにする**。

**v3.2 で境界が 1 段細かくなった** Apple カタログの取り込み（FR-01b）を有効化すると、**Apple のみに存在するアーティストは Apple が失うと検索からも消える**――これは精度の劣化ではなく、機能の一部喪失である。したがって Apple は「純粋な強化層」ではなく **一部を原点に食い込ませた状態** になり、加入が確定しているので受け入れるが、**曖昧にせず明言する**。

一方で **CC0 の 4 ソースだけで製品が成立する構造は変わらない**――MusicBrainz 由来の 298 万件とその類似度グラフは Apple と無関係に存在し、失ったときに戻す先がある。この境界を引いておく意味である。

**それ以外の点では、この境界は維持される** 理由は撤退可能性の確保だけではない――**どのデータがどの契約の下にあるかを、常にテーブルの `source` 列で言えるようにしておく」こと自体に価値がある。要求が改定されたときに影響範囲を調べるのではなく、**最初から分かっている** 状態になる（§3.5.6 項目 4）。

**試聴レビューの廃止はそれとは別の話である**。v2.1 の設計時点で縮退経路（FR-23）を常に実装済みに保つと決めていたため（旧 ADR-13）、v3.0 の変更は **すでに用意されていた分岐のうち縮退側を正式構成として選び直しただけ** である。失われたものは、1 秒で当たりを判断できる速さであり、これは体験上の損失として明確に切り分けている（§12 の R-36）。

### 3.2 採用するデータソースとライセンス

**ライセンスは「データソース単位」ではなく「データの部位単位」で判定する** 同じ提供元でも、部位によって取得経路によって商用利用の可否が変わるためである。

**原点（CC0）**――これだけで製品が成立するほう

| データソース | 取得する部位 | ライセンス | 申請 | 用途 |
| --- | --- | --- | --- | --- |
| **MusicBrainz** コアデータ（`mbdump`） | アーティスト実体、別名、活動年代、関係（メンバー・共演・レーベル）、**URL 関係**、**バーコード / ISRC** | CC0 | 不要 | 全項のの主キー、関係信号、外部 ID の種 |
| ~~MusicBrainz 補足データ~~ | ~~タグ（ジャンル関連付けを含む）、レーティング、アノテーション~~ | **CC BY-NC-SA 3.0** | ─ | **v3.0 で不採用**（下記） |
| **ListenBrainz** リスニングログ | 再生履歴（匿名集計） | CC0 | 不要 | 共聴（セッション共起）に基づく類似度 |
| **Discogs** 月次データダンプ | Genre / Style、レーベル、単一リリースの共演 | CC0 | 不要 | **ジャンル階層の骨格**、レーベル信号 |
| **Wikidata** | `P737 influenced by`、`P136 genre`、`P279 subclass of`、活動年代 | CC0 | 不要 | 影響信号、ジャンルの補完 |

**強化層（Apple）**――あれば良いくなくても成立するほう

| データソース | 取得する部位 | ライセンス | 契約 | 用途 |
| --- | --- | --- | --- | --- |
| **Apple Music Feed**（v3.0 で新設） | `artist` / `album` / `popularityTopChartAlbums` の各エクスポート | Apple 提供データ（**CC0 ではない**） | **Apple Developer Program への加入**（v3.1 で確定） | 人気度、Apple Music アーティスト ID、**別名（多言語表記）**、ジャンルの補完、リリース年・レーベルの補完、**カタログの取り込み（FR-01b・OI-37 待ち）** |

**CC0 は著作権とデータベース権を放棄した状態であり、複製・改変・再利用・再配布のいずれにも許諾を要らない。** 帰属表示も法的義務ではないが、コミュニティへの敬意として設定画面にはクレジットを掲載する（画面設計書 §5.8）。**Apple Music Feed のデータは CC0 ではなく、Apple Developer Program の契約下で利用するものである**――この区別を §3.5.2 で定める。

**v3.0 でジャンルの出所を変えた理由**\: MusicBrainz のジャンル関連付けは **利用者が付けたタグに由来する補足データとして CC BY-NC-SA 3.0** が適用される。NC は非商用限定を意味するため、有料サブスクリプションを持つ DIGGR では使えない。

MusicBrainz の `genre` **エンティティ自体**（ジャンル名の一覧）はコアデータで CC0 だが、**そのアーティストがシューゲイザーであるという結び付き** が非商用側にあり、使いたいのは後者なので、これは実質的に使えないということになる。

代替として **Discogs の Genre / Style（CC0）を骨格、Wikidata の `P136 genre`（CC0）を補完** とする。Discogs の Style は約 500 種と粒度が細かく、サブジャンルの島レイアウト（FR-29）との相性が良い。ジャンル信号の重み 0.20 は残し置く係数の再調整は Phase 0 の評価（OI-11）で行う。

**「ダンプを保持すること」と「ライブ API を借りること」は別の行為である**。CC0 データを自社基盤で運用する行為には何の許諾も要らない。一方、MetaBrainz のライブデータフィード（レプリケーション）や Discogs の API を商用で継続利用する場合は、サポーター契約や個別の相談が生じる。**本設計は原則だけに依存する**――Apple Music Feed を含めてすべて一括エクスポートの取得で完結する。**実行時に外部 API を借りない**。詳細は §3.5。

### 3.3 聴く手段の選定と除外したサービス

| サービス | 判定 | 理由 |
| --- | --- | --- |
| **外部アプリへのディープリンク** | **採用（FR-23）** | 公開 URL を開くだけ。API キー・OAuth・SDK・規約同意・審査・レート制限のいずれも不要 |
| **Apple Music Feed** | **採用（データソース）** | 月次パイプラインでカタログメタデータを一括取得する（§3.2 / §6.2.1）。**聴く手段ではなくデータ強化の層**であり、FR-23 の実装には関与しない |
| ~~iTunes Search API~~ | **不採用（v3.0）** | 試聴レビューと共に廃止（§3.1.2）。ポート登録と、音声を保存しないプロセス、ストアリンク近接配置などの実装制約を負わずに済む |
| Spotify Web API | 不採用 | 商用利用には拡張アクセスの申請と承認が要る。加えて Developer Policy が、Spotify のコア体験の模倣・置換、Spotify コンテンツを分析した派生機能の作成、他サービスのコンテンツとの統合を禁じており、DIGGR の中核と正面から衝突する。詳細は §3.5.5 |
| Last.fm API | 不採用 | 既定ライセンスが非商用限定。商用利用には個別の申請と契約が必要。共聴信号は ListenBrainz（CC0）で代替できる |
| Deezer API | 不採用 | 利用規約が非商用目的・非商用環境にのみ明示的に限定されている |
| YouTube Data API | 不採用 | 既定のクォーターでは検索が 1 日約 100 件が境界には監査申請が必要 |

**聴く体験は一層になった**。v2.4 ではアプリ内 30 秒プレビューで聴く判断をし、気に入ったら外部アプリでフル尺、という二層構成だったが、v3.0 では後者だけが残る。

**この損失を埋めるのは「地図そのものの情報量」である**。ノードの大きさ（類似度）、エッジの種別（どう関連するか）、ジャンル色、閲覧済みチェックによって、**聴く前に当てを付けさせる情報が画面上に増える**。試聴を失っている以上、聴く前の役割が視覚情報に移す設計とする。

#### 3.5.5 採用しなかったサービスとその理由

**Spotify Web API** — 月次パイプラインのデータソースとして検討したが、以下の理由で不採用とする。

| # | 論点 | 内容 |
| --- | --- | --- |
| 1 | **必要な機能がそもそも提供されない** | Related Artists・Recommendations・Audio Features を含む 8 エンドポイントが、2024 年 11 月 27 日以降に登録された新規アプリケーションには提供されない。DIGGR が欲しかった「関連アーティスト」は、承認を得ても取得できない |
| 2 | **商用利用は承認制** | Development Mode は 2026 年 2 月以降、Premium アカウント必須・認可ユーザー 5 人まで・**非商用の個人利用に限定**。商用は拡張アクセスの申請と承認が要る。申請なし商用利用の原則に反する |
| 3 | **Developer Policy との衝突** | 同ポリシーは ④ Spotify のコア体験の模倣・置換 ⑤ Spotify コンテンツを分析して派生的な指標・機能を作ること ⑥ 他サービスのコンテンツとの統合 ⑦ 機械学習モデルへの投入 を禁じている。**関連アーティストの可視化は Spotify のコア体験そのもの** であり、④⑤⑥ に同時に触れる |
| 4 | **収益モデルとの衝突** | 非ストリーミングアプリで許されるのは再生や広告・スポンサーシップ等に限られ、コンテンツへのアクセスに紐づくアプリ内課金は許されない。DIGGR の「解放件数を増やす」サブスクリプションは、まさにこれに該当する |

**したがって Spotify との関わりは「リンクを貼るに徹する」のが唯一の適法な形である**。§3.5.3 のとおり、v3.0 ではこのリンクの精度を上げた――**Spotify のデータを借りるより、Spotify への導線だけを良くする**ほうを選んだ。これは規約上の妥協ではなく、この制約下での最適解である。

なおこの判断は Spotify に限った話ではない。**主要ストリーミングサービスはおおむね、自社の推薦・発見機能と競合する用途をポリシーで禁じている。** 発見体験を自分で作る以上、データを自分で持つ以外に道はない――これが v2.0 の結論であり、v3.0 でも変わらない。

**その他** — Last.fm（非商用限定）、Deezer（非商用限定）、YouTube Data API（クォータ増枠に監査申請）、iTunes Search API（v3.0 で廃止・§3.1.2）。

**Apple を採ってSpotify を採らないのは、不公平ではなく構造の違いである**。

| 観点 | Spotify | Apple Music Feed |
| --- | --- | --- |
| 商用利用の可否 | 拡張アクセスの**承認制** | 会員資格があれば**自己構成で有効化** |
| その契約は別途必要か | Spotify のためだけに発生する | **iOS 配信のためにどのみち必要** |
| 中核機能との衝突 | 関連アーティストの可視化は Spotify のコア体験の模倣にあたる | **強化層のメタデータであり、発見機能そのものを Apple から借りていない** |
| 失ったとき | ─ | **地図は消えない**。並び順の精度とリンクのカバレッジが下がるだけ |

この 4 行目が最も重要である。**Apple を採っても中核機能が人質に取られない**――類似度の 5 信号もジャンル階層の骨格も CC0 側に置いたままにしていることの帰結である（§3.1.2）。

### 4.2 主要機能の詳細（聴く機能 → 探す機能の順）

#### FR-01 アーティスト検索（検索対象の範囲）

**v3.2 で検索対象を二層にした。** 見つけることと、地図を描くことは必要なデータが違うので、範囲を分ける。

| 層 | 対象 | 必要なデータ | 地図の種類 |
| --- | --- | --- | --- |
| **検索・同定層** | **全アーティスト** | 名称、別名、ジャンル、外部リンク | ─ |
| グラフ層 | **信号のあるアーティスト**（`has_graph = true`） | 類似度 5 信号 | **関連アーティスト地図**（FR-02） |
| グラフなし | 残り | ジャンルのみ | **ジャンル地図にフォールバック**（FR-29） |

**検索対象の内訳**

| 内訳 | 件数 | 備考 |
| --- | --- | --- |
| MusicBrainz | 約 298 万件 | 2026 年 9 月時点の全件（実測値） |
| **Apple Music Feed（MusicBrainz にない分）** | **約 900 万件（見込み）** | **Phase 0 で実測（OI-43）。OI-37 の結果による**（下記） |
| **検索できるもの合計** | **約 1,200 万件** | **FR-01b 有効時。現行の約 4 倍** |
| うち `has_graph = true` | **100〜200 万件** | 関連アーティスト地図（FR-02）を描ける範囲 |

**900 万件という見込みの根拠**\: Apple Music のカタログは 1 曲投稿で Spotify と同規模である。Spotify の公開レポート（Loud & Clear 2025）では **1 曲以上を配信しているアーティストが約 1,300 万人**、**年間 1,000 回再生以上の曲を 1 つ以上持つのが約 350 万人** とされる。これをもとに Apple 側の総アーティスト数を **1,100〜1,300 万件**、MusicBrainz との重複を **150〜200 万件** と置き、差分を **約 900 万件** とする。

**ただし増える 900 万件の大半は、曲数 10 未満の層である**。実用上意味のある増分は、**商業流通していて MusicBrainz にまだ登録されていない 150〜250 万件**――新譜と非英語圏――だと見ている。1,200 万という総数は、カタログの広さであって、体験の改善幅ではない。

**この数字は見積もりであり、確定値は Phase 0（OI-43）で実測する**。フィードは既にダウンロードしているので、数える作業だけで済む。

**「人気上位 200 万件」という順位での切り方をやめた。** v3.1 まではカタログ自体が人気上位 200 万件に切っていたが、これには 2 つ問題があった。

① **順位は恣意的である**。200 万位と 200 万 1 位の間に意味のある差はない。

② **検索に必要な容量はそもそも軽い**。名称・別名・ジャンル・リンクで **200 万件あたり 2.7GB**、全 298 万件に広げても **約 1.4GB** にしかならない。重いのは類似度データ（26GB）であって、アーティスト実体ではない。

だから **検索は全件、グラフは質で絞る**。切り方は順位ではなく **「共聴データが 1 件以上」または Discogs のリリースが 1 件以上」という客観的な基準** で行う（閾値は OI-44）。

**仕様**

- 名称・別名の部分一致によるインクリメンタル検索（`pg_trgm`）
- **結果の並び順は `popularity` 降順**。`has_graph` の有無では並べ替えない
- **グラフの有無を UI で区別しない**。選んだ後に地図の種類が変わるだけである（画面設計書 §5.1）
- ジャンルを横断して候補に含める

**検索できるのに地図が出せないという状態を作らない**。グラフの無いアーティストを選んだときは、**そのアーティストのジャンルを「シード」とするジャンル地図**（FR-29）を返す。島レイアウトがそのまま効くので、**新しい実装はほぼ要らない**。

R-12（ロング・非英語圏アーティストのデータ希薄→ジャンル起点タグへ誘導）として方針だけ書いてあったものが、**データ構造の側から裏付けられた形である**。

#### FR-01b Apple カタログの取り込み

**この機能は OI-37（契約）と OI-38（重複率）の両方を満たすときに有効化する。** 実装はすでにあり、フラグで切り替える。

| ゲート | 確認事項 | 満たさない場合 |
| --- | --- | --- |
| **OI-37** | Apple 由来のアーティスト名をクライアントに表示している | 有効化しない（R-41） |
| **OI-38** | 検索結果の重複率が 2% 未満に収まる | 有効化しない（R-40） |

| フラグ | 振る舞い |
| --- | --- |
| `APPLE_CATALOG_SEARCH = false`（既定値） | **v3.1 と同じ**。Apple は強化層のみ、突合できなかった Apple アーティストは取り込まれない |
| `APPLE_CATALOG_SEARCH = true` | Apple のみのアーティストを `artists` に入れ、検索対象になる |

**なぜフラグにするのか**。Apple 由来のアーティストが検索結果として見えるのは、これまでの **強化（enrichment）ではなく、カタログの再配布に近づく行為** である。現行の §3.5.6 項目 4 は、Apple のレコードをそのまま返す経路を作らないことを求めている。

Apple Music Feed はカタログ閲覧体験を作るために提供されている仕組みなので通す見込みはあるが、**推測で進める場所ではない**。契約本文を読むのは Phase 0 であり、それまでにパイプラインと UI は仕上げておく――**旧 FR-06 の `PREVIEW_ENABLED` で行ったこと（縮退を待っていたこと）と、フラグ 1 つで切り替えったのと同じ形である**。

**有効化したときに変わること**

| 項目 | 変化 |
| --- | --- |
| **検索対象の件数** | **約 298 万件 → 約 1,200 万件**（FR-01）。ただし `has_graph = true` は 100〜200 万件のまま増えない |
| 検索で見つかる範囲 | **新譜と非英語圏に強くなる**。MusicBrainz はボランティア編集なので、この 2 つに弱い |
| **DB 容量** | **＋約 4.5GB**（§7.3）。VPS の 80GB SSD の残余が細まる（技術選定書 §9.3） |
| **Apple の位置づけ** | **強化層からも部分的に原点へ**（§3.1.2）。失うとそのアーティストが検索から消える |
| **重複リスク** | **UPC 番号照合（OI-38）が検索品質を直接決める**。継すれば同じアーティストが 2 行出る（R-40） |

**Apple のみのアーティストにも完全にデータが無いわけではない。** `album` フィードから以下が取れる。

| 使い道 | 使う理由 |
| --- | --- |
| `genres`（`path` 付き） | **ジャンル地図を描ける** |
| `artistRoles` / `primaryArtists` | **共演エッジを引く** |
| `recordLabels` | 同レーベル信号 |
| `releaseDate` | 年代フィルタ（FR-22） |

取れないのは **共聴（重み 0.50）** である――ListenBrainz は MBID をキーにしているため、`has_graph = false` とし関連アーティスト地図は作らない。

### 4.2 FR-02 マップ生成（確定枠・外側）

マップは「必ず含む部分」とその「外側」の 2 層で組み立てる。

**二層構造**

| 層 | 定義 | 性質 |
| --- | --- | --- |
| **確定枠（core）** | 同事類似度スコア **0.60 以上** の強関連 | 同じシードなら常に同じ順番が固定 |
| **外側（random）** | 確定枠に入らなかった関連アーティストのプール | **ランダム表示（FR-30）が ON のときだけ抽選になる** |

**ノード数と確定枠の上限はプラン**

| プラン | ノード上限 | 確定枠の上限 | 外側の最低保証 |
| --- | --- | --- | --- |
| Free | **30 件** | **20 件** | **10 件** |
| Pro | **100 件** | 40 件 | 60 件 |

クランプで溢れた確定枠は、**プールの先頭に戻す**。消すのではなく、引ける候補として残す。

**v3.0 で上限を 150 → 100 に下げた**。Android 実機での検証の結果である。問題は描画フレームレートではなく **ラベルの可読性** だった――150 件を同じ面積に置くと、拡大しても名前が読めない領域が残る。

**ノードを減らす代わりに、ラベル幅を見込んだ間隔を取る**（画面設計書 §4.7）。100 件なら、拡大していけば、すべての名前に到達できる。**読めない 150 件よりも読める 100 件のほうが情報量が多い**。

**プールの範囲**

外側の抽出元は **そのシードと何らかの関連があるアーティスト群（類似度 41〜650 位、最大 610 件）** とする。カタログ全体からの無制限ランダムではなく、298 万件からランダムに引くとシューゲイザーを持っていても関連のに脈絡が混ざり、発見ではなく壊れているものと受け取られる。

**組み立てアルゴリズム**

1. 確定枠をスコア降順で並べ、クランプ上限で切る
2. 溢れた確定枠をプールの先頭に連結する
3. 残スロット数 = ノード上限 − 確定枠件数
4. **ランダム表示 OFF（既定）**ならプールの先頭から残スロット数だけ順に取る（類似度順・人気順の続き）
5. **ランダム表示 ON** なら、プールから残スロット数だけ、**重みを付けずに無復元抽出**する。抽出には毎シードごとの乱数シードを使う（FR-02b）

プールが残スロット数を上回らないレアなアーティストでは、プール全件を使って埋める（水増しはしない）。

**閾値 0.60 の根拠**\: Phase 0 の初期評価（OI-11 / OI-31）で確定させる仮設定値として外出しし、リリース後も調整できるようにする。

**ジャンルそのものに確定枠はない**（`core_count = 0`）。全件が同じ資格（そのジャンルに属すること）で選ばれているためである（FR-29）。

#### FR-02b マップの同定方式

ランダム枠を導入すると、**「あの人が見えた地図」をもう一度見ることが自明でなくなる**。履歴から戻る、ブックマークを開く、引き直しの系譜を辿る のすべてが、もろもろが一意に同定する仕組みを設ける。

| 要素 | 内容 | 用途 |
| --- | --- | --- |
| `map_id` | マップの一意 ID（ULID） | 履歴・ブックマークのキー |
| `node_uids` | **生成された最大 100 件の `uid` 集合（順番付き）** | 完全再現の根拠。これが正となる |
| `random_seed` | 抽出に使った 64bit 乱数シード | 系譜の記録と再生成の検証 |
| `schema_version` | 生成時の音楽グラフスキーマ版 | データ更新をまたいだ差分の検知 |
| `core_count` | 確定枠の件数 | 表示中の境界と、無料ユーザーへの遮蔽判定 |

**シードではなく、ノード集合を正とする**。乱数シードだけを保存して都度再生成する方式は軽いが、**月次のデータ更新でプールの中身が変わると同じシードで違う結果になる**。一週間前の履歴を開いたら別のマップが出るのは、履歴機能として成立しない。

`uid` の集合は 100 件 × 16 バイト = 約 1.6KB。DAU 1,000 で 1 年蓄積しても 8GB 程度である。**安いコストで完全再現を買う**。

この仕組みは、リリース後の地図共有（§11.2）を実装する際の下地になるが、**共有がなくても、履歴・ブックマーク・引き直しのために単独で必要**であり、先行実装しても無駄にはならない。

### FR-27 マップの引き直し

同じシードで外側を再抽出し、別のマップを得る。

- **ランダム表示（FR-30）が ON のときだけ有効**。OFF は決定的な並びなので、引き直し対象が存在しない
- 新しい `random_seed` を発番する。確定枠はそのままに、外側だけを引き直す
- アニメーションとして、外側のノードを一度消して新しい顔ぶれを出現させる（確定枠は動かない）
- 引き直しは **新しいマップとして履歴に残る**。元のマップにも戻れる
- 回数制限は設けない、自社 DB へのクエリだけで完結する
- 判定式は `canReroll = randomOn && pool.length > slots`。満たさないときは ⋮ メニューの項目を非活性にする

**v2.4 では「単一ジャンルかつ無料なら無効」という区分だった**。v3.0 ではランダム表示がプランではなくユーザーの選択になったため、**判定がプランと無関係に単純化された**。ジャンルもろは常に全件ランダムなので、ランダム表示の ON/OFF に関わらず引き直せる。

### FR-28 段階表示（10 件ずつ）

もろもろが一気に全件出るのではなく、ユーザーのペースで 10 件ずつ開いていく。

| 項目 | 仕様 |
| --- | --- |
| 初期表示 | **10 件** |
| 1 回の押下 | 次の 10 件を追加、既存のノードは消えない |
| 順序（関連もろも） | 確定枠（スコア降順）→ 外側（決定順または抽出順） |
| 順序（ジャンルもろも） | **島をまたいで round-robin**。早くに全体の広がりが見える |
| 押せる回数 | Free: 3 回で 30 件上限、Pro: **10 回で 100 件上限** |
| 上限到達時（Free） | ボタンが **「もっとディグる」（＋70）」に変わり、ペイウォール（SC-09）への導線になる |
| 上限到達時（Pro） | ボタンが「全件表示中」の非活性状態になる |
| 一括表示 | ボタンの長押しで権利範囲の全件を一度に開く |
| 引き直し時 | 表示件数は 10 件にリセットされる |
| 履歴から復帰したとき | **前回開いていた件数を復元する** |

**データ取得との関係**\: 段階表示は **完全にクライアント側の描画制御**である。API は権利範囲の全件を一度に返す。**ボタンを押しても、通信は発生せずカメラも動かない**。

**この機能は 3 つの問題を同時に解く**。

① **描画負荷**。100 件を初期描画する必要がなくなる。

② **情報の洪水**。一気に出すとどこから見ればいいか分からなくなる。近い順に 10 件ずつ開けば、**ユーザーが自分で深さを選べる**。

③ **課金導線**。無料ユーザーが 3 回押したところで同じボタンが「＋70」に変わる。**ボタンを押すリズムだけで上がったところで壊れる見せ方**なので、別の場所に置く課金より自然に機能する。

### FR-29 表示タイプ切替

同じシードに対して、周囲に並べるアーティストの選び方を 2 タイプから選べる。

|  | **関連アーティスト**（既定） | **同じジャンル** |
| --- | --- | --- |
| 選択基準 | 同事類似度 | シードの主ジャンルに属すること |
| 形 | 中心からの放射状、確定枠が内側 | **サブジャンルごとの島** |
| 確定枠 | あり | **なし**。全件がランダム枠 |
| ノード取得 | 類似度が高いほど大きい | 一定 |
| 顔ぶれ | 類似度順 | **関連もろもに出た人を後ろに回す** |
| エッジ | 関係タイプを色で区別（FR-21） | 中心からの放射線のみ |
| 中心アイコン | 人マーク | **人マーク**（v3.0 で統一） |

**仕様**

- シードが複数ジャンルを持つ場合、`artist_genres.weight` 最大のジャンルを主ジャンルとする。ジャンルパネル（SC-07）で別のジャンルを選べばそちらに切り替わる
- **シードが `has_graph = false` のときは `related` を選択できない**。切替は「同じジャンル」が選択済みの状態で開く。`related` 側は無効化される（FR-01 / 画面設計書 §5.2）
- 切替は **新しいマップとして生成される**（`view_type` を含めて `maps` に保存）
- **往復しても結果は保持される**。履歴から同一 `seed_key` × `view_type` のものを引き当てて復帰する（v3.0 で修正）

**v3.0 でこの 2 タイプがまるで異なる地図になった**。v2.3 で導入した時点では、同じ顔ぶれを同じ形で並ぶだけのものだったが、**軸を変える意味が伝わらなかった**。一つの手を重ねて差別化している。

① **形を変える**――放射状からサブジャンルの島レイアウトへ、一目で別の地図だと分かる。

② **顔ぶれを変える**――関連もろもに出た `uid`（`knownUids`）を後ろに回す、**無料 30 件で重複 0%** を確認済み。

③ **順番を変える**――島をまたいで round-robin に出すので、段階表示の早い段階で **ジャンルの広がりそのもの** が見える。

関連アーティストは「この人が好きな人は他に何を聴いているか」、同じジャンルは「この音の仲間は他に誰がいるか」という**前者はリスナー軸、後者は音楽軸の探索**であり、地図の形も中身も違ってきていい。

### FR-30 ランダム表示オプション

外側（ランダム枠）が抽選になるかどうかを**検索時にユーザーが選ぶ**。

|  | OFF（既定） | ON |
| --- | --- | --- |
| 外側の決まり方 | 類似度順・人気順の続き | プールからの抽選 |
| 同じ検索を繰り返したとき | **常に同じ結果** | `random_seed` から完全再現 |
| 引き直し（FR-27） | **不可** | 可 |
| `random_seed` | 0 を保存 | 生成した値を保存 |

- トグルはホーム画面（SC-03）の検索本の下に置く。選択は端末に保存する
- 確定枠は ON/OFF に関わらず変わらない。変わるのは外側だけである
- **ジャンルもろもろは、この設定に関わらず常に全件ランダム**。ジャンルを掘る行為は、そもそもそれが誰かも知らない顔ぶれに会いに行くことを意味しているためである

**v2.2〜v2.4 はランダムを既定としていたが、これは裏目だった**。βが触って分かったのは、**同じアーティストを検索したのに結果が違うと、まず不信につながる**という、当たり前に見えることの再発見が、発見ではなく事故に見えるということだった。

決定的な並びを既定にした、**ランダムは「そういうもの」だと知った上で選ぶものにした**。ランダムそのものと、選んだつもりが結果が変わったこと自体がユーザーの期待に、同じ仕様でも受け取りやが逆転する。

### FR-31 チェック済み表示

詳細シート（SC-06）を開いたアーティストに印を付ける。**地図のどこまで見たかを失われないようにする**。

- 詳細シートを開いた時点で `checked` に入る（長押しで開いた場合は入れない）
- ノードの右上に **白丸（チェック）** を持つ
- 既聴（外部アプリへ遷移した）とは別の状態である。**見たと聴いたは違う**
- **`checked` はアーティスト単位で保存する**。別のシードから到達しても、印は付けたままである（§7.4）

**100 ノードを拡大・移動しながら見ていると、どこを見たか分からなくなる**。これはβ実装が触って初めて分かった問題で、仕様上の推論からは出てこなかった。**地図を歩く体験には、足跡が要る**。

## 5. 主要ユースケース

### UC-01 初回ディグ（無料ユーザー）

1. アプリ起動 → オンボーディング（3画面を最後に普段使い音楽アプリを選択）→ 検索画面
2. 「Radiohead」と入力 → 候補リストから選択、ランダム表示は **既定で OFF**（FR-30）
3. マップ画面へ遷移、中心に Radiohead（人アイコン・グロー）、周囲に **30 件**（確定枠 18 件・外側 12 件）のうち、まず **10 件** をルートが伸びながら出現する
4. 下部に「＋ さらに 10 件」と「あと 20 件」のボタン、その上にジャンル・組み込・中心に戻るの 3 つ
5. 任意のノードをタップ → 詳細シートを開く、**同時にチェック済みになる**（FR-31）
6. シートには関係性の説明（「共聴」「共演」など）と、音楽アプリへの導線が並ぶ
7. 気になったらそこで聴く → 選択した音楽アプリを **そのアーティストのページ** で開く（FR-23）
8. DIGGR に戻ると、もろもろはそのまま、見たノードに既聴マークが付く
9. バンドで拡大すると、隠れていたアーティスト名が現れる。ラベルは指の動きに追従し、消えない

**v3.0 で UC-01 からプレビュー再生を消した**。代わりに入ったのは、ステップ 5 のチェック済みと、ステップ 9 の拡大である。**「考えて判断させる」から「見て当てを付けさせる」へ、判断の場所が移った**。それが成立するかは Phase 1 の検証項目である（R-36）。

**ステップ 2 でランダムを選ばなかったユーザーは、引き直し（FR-27）に到達しない**。それは意図した設計である――初回体験ではまず「そのアーティストの周りには、これだけ関連がある」という正確な地図を見せる。**引き直しは「もっと知らない顔ぶれを見たい」と思ったユーザーのための機能**に位置づける。オンボーディングの 3 枚目でランダム表示の存在を一度だけ伝える。

### UC-02 課金による全解放

1. 段階表示ボタンを 3 回押して 30 件を開き切ったとき、同じボタンが「もっとディグる」（＋70）」に変わる → タップしてペイウォール
2. プラン選択（年額／月額）→ ストア課金シート → 購入完了
3. RevenueCat Webhook が API サーバーに通知 → `entitlements` テーブル更新（`node_limit` = 100）
4. アプリが権利を再取得すると、**同じマップが広がる**。すでに見えていたノードは順序ごと残り、増えた分だけ後ろに足す（`expandMap`）

重要なのは **もろもろが引き直されない** ことだ。`maps.node_uids` には生成時の 100 件分が保存されているため、課金すると **今まで見ていたそのもろの続き** が現れる。別のもろになってしまうと、課金直前に見ていた顔ぶれと見比べたい対象が失われ、課金体験が損なわれる。

### UC-03 軸を変える（関連 → 同じジャンル）

1. マップ上部のセグメントで「同じジャンル」を選ぶ（FR-29）
2. 地図が **サブジャンルの島** に組み直される、関連もろもとは別の顔ぶれが並ぶ
3. 段階表示ボタンを押すと、島をまたいで 10 件ずつ出す。早い段階でジャンル全体の広がりが見える
4. 「関連アーティスト」に戻る → **さっきの地図がそのまま復帰する**。往復しても再抽出しない

**ステップ 4 は v3.0 での修正項目である**。β実装では復帰の度に再生成していて、**「戻ってきたら別の地図になっている」**という振る舞いだった。履歴から同一 `seedKey` × `viewType` のもろもろを引き当てて復帰することで解消した。

これは **もろもろがノード集合で同定している（FR-02b）からこそ可能な修正** である。乱数シードだけを保存する設計だったら、復帰は再抽出になり、月次更新をまたいだと同じ問題が再発していた。

### UC-04 引き直し

1. 検索時に **ランダム表示を ON** にしてもろもろを生成する（FR-30）
2. 外側が上限に見える ⋮ メニュー → 「🎲 引き直し」
3. **確定枠は変わらず、外側だけが別の顔ぶれに入れ替わる**（FR-27）
4. 引き直したもろもろは新しい履歴として残る。元のもろもろにも戻れる

ランダム表示が OFF のときは、⋮ メニューの引き直しは非活性である。

## 6. システム構成

### 6.1 論理構成

| レイヤ | 構成要素 | 責務 |
| --- | --- | --- |
| ドメイン層 | `packages/core`（TypeScript、UI 非依存） | もろもろ生成・二層構造・乱数レイアウト・ラベル配置。**アプリとサーバーが同じコードを使う** |
| クライアント | `apps/mobile`（Expo / React Native） | 描画・操作・課金 SDK・外部アプリ連携 |
| **端末データストア** | **expo-sqlite** | **履歴・ブックマーク・チェック済み・聴いた記録の保持とアーティストのキャッシュ**（§7.4） |
| API サーバー | `services/api`（Fastify + Node.js） | 検索・もろもろ生成・権利判定・件数制御 |
| キャッシュ | Redis | もろもろ結果・検索候補・ジャンル所属一覧 |
| 永続層 | PostgreSQL | 音楽グラフ・ユーザー・権利・履歴 |
| データパイプライン | 月次バッチ | CC0 ダンプの取得・正規化・類似度計算・外部 ID 解決・DB 挿入 |
| 外部 | RevenueCat、AdMob | 課金・広告 |

**v3.0 で外部依存が 2 つになった**。v2.4 の表にあった iTunes Search API とバックグラウンドワーカーは消え、残るのは **課金と広告だけ** である。この 2 つは事業の前提であり、代替不可能な依存として切り分ける。

**ドメイン層を切り出したのが v3.0 の構造上の最大の変更である**。もろもろ生成のロジックを UI とサーバーの両方に散らばっていると、件数制御や抽出の仕様が 2 箇所に存在して忘れられる。`packages/core` に寄せることで、**UI を起動せずに仕様をテストで検証できる**。

### 6.2 データパイプライン

v3.0 では、もろもろは **月次の音楽グラフパイプライン 1 本だけ** である。v2.4 にあった常駐のバックグラウンドワーカーは、試聴レビューの廃止（§3.1.2）とともに不要になった。ユーザーのリクエスト経路とは完全に分離されている。

#### 6.2.1 音楽グラフパイプライン（月次・一本）

| # | ステップ | 内容 |
| --- | --- | --- |
| 1 | 取得（CC0） | MusicBrainz / ListenBrainz / Discogs / Wikidata の公開ダンプをオブジェクトストレージへ |
| **1b** | **取得（Apple）** | **Apple Music Feed の `artist` / `album` / `popularityTopChartAlbums` エクスポートを取得**（下記） |
| 2 | 抽出 | 必要なエンティティのみ抽出。**対象テーブルはホワイトリスト方式とし、MusicBrainz の `tag` 系を明示的に除外**（§3.5.6 項目 2） |
| 3 | 同定 | MBID をキーに各ソースを突き合わせ、**`uid` を確定する**（§7.1.0） |
| **3b** | **Apple の突合** | **Apple のアーティスト ID を MBID に紐付ける**（下記） |
| 4 | ジャンル構築 | **Discogs の Genre / Style を骨格とし、Wikidata の `P136` と Apple の `genres.path` で補完して** `artist_genres` を作る |
| 5 | 類似度計算 | 5 信号の重み付き合成、上位 650 位まで算出 |
| 6 | 二層分割 | 上位 40 件を `artist_similarity`（行）に、41〜650 位を `artist_pool`（集合）に振り分け |
| 7 | 外部 ID 解決 | MusicBrainz の URL 関係から Spotify / Apple Music / YouTube Music の ID を抽出、**ステップ 3b の結果とマージして** `artist_external_links` に格納 |
| **7b** | **人気度の算出** | **Apple のチャートデータと ListenBrainz の再生回数を合成して** `artists.popularity` を確定する |
| 8 | 階層構築 | ジャンル階層テーブルの生成（FR-10） |
| 9 | 挿入 | 新スキーマへ書き込み後、アトミックに切り替え |
| 10 | 検証 | 件数・分布・代表クエリの回帰チェック |

**ステップ 1b: Apple Music Feed の取得（v3.0 で新設）**

Apple Music Feed はカタログメタデータを **Parquet の分割ファイルとして一括配布する** 仕組みである。アーティストを 1 件ずつ取り合わせる方式ではなく、ほかの 4 ソースと同じ手順で扱える。

1. Media Services キーで JWT（開発者トークン）を署名する
2. `GET https://api.media.apple.com/v1/feed/{feedId}/latest` で最新エクスポートの `id` を得る
3. `GET /v1/feed/exports/{id}/parts` で分割ファイルの `exportLocation` 一覧を得る
4. 各 URL から Parquet をダウンロードする。**`exportLocation` は有効期限付き** なので、取得したものはその足で使い切る

| `feedId` | 含むもの | 用途 |
| --- | --- | --- |
| `artist` | Apple アーティスト ID、名称（多言語）、`urlTemplate` | 外部リンク解決（FR-23）、**別名の拡張**（下記） |
| `album` | `upc`、`primaryArtists`、`artistRoles`、`genres`（`path` 付き）、`recordLabels`、`releaseDate` | **MBID との突合キー**、ジャンル補完・レーベル・年代の補完 |
| `popularityTopChartAlbums` | チャート順位 | `artists.popularity` の算出 |

**ステップ 3b: Apple アーティスト ID と MBID の突合**

| 優先 | 方法 | 根拠 | 確度 |
| --- | --- | --- | --- |
| 1 | MusicBrainz の URL 関係に `music.apple.com/.../artist/{id}` がある | CC0 の直接リンク | **確定** |
| 2 | **アルバムの `upc` が MusicBrainz のリリースのバーコードと一致** → そのリリースのアーティストと結ぶ | 世界共通の商品コード | **高** |
| 3 | 名称の正規化一致 ＋ 活動年代・レーベルの補強 | ヒューリスティック | 中（スコア閾値以上のみ採用） |

**別名の拡張（v3.1 で追加）**

`artist` フィードの名称は **ロケールごとのキーを持つ**。MusicBrainz の別名（`aliases`）に、Apple 側の多言語表記を突き合わせて追加する。

| 効果 | 内容 |
| --- | --- |
| **日本語での検索** | 「ビョーク」で Björk を引ける。表記を知らなくても届く |
| 表示は変わらない | アーティスト名は原表記のままレンダリングする（§10 の国際化方針）。**別名は検索の入口としてのみ使う** |
| **再配布はしない** | Apple 由来の別名は **サーバー側の検索インデックスに宛てる**。クライアントへ送るのは CC0 由来の別名だけである（§3.5.6 項目 4 / §7.1 の `artist_aliases`） |

**UPC を突合キーに使うのがこの設計の芯である**。MusicBrainz はリリースにバーコード（UPC / EAN）を保持しており、Apple Music Feed のアルバムにも `upc` が入っている。**これは両者が独立に付与した ID ではなく、業界共通の商品コードである**――つまり名前の推測なしに確定に結ぶ。

さらに、**MusicBrainz に Apple へのリンクが登録されていないアーティストでも ID が拾える**。リンクの登録率は人気アーティストに偏っているので、**この補完が効くのは まさにディグの価値が高い領域** である。

**既存マップスキームの再配布の影響を受けない**。`maps.node_uids` にノード集合が保存されているため、月次でデータが更新されても、履歴は当時のまま再現される。アーティスト名・ジャンル・外部リンクなどの表示情報だけが最新になる。

**Apple Music Feed の取得に失敗してもパイプラインは止めない**。ステップ 1b / 3b / 7b はいずれもスキップ可能とし、前回スキーットの値を引き継いで完走する。引き継ぐのは `artist_external_links`、`popularity`、および **FR-01b 有効時は `source = 'apple'` の `artists` / `artist_aliases` / `artist_genres` の該当行** である――**引き継ぎ忘れると、Apple のみのアーティストが検索から一時に消える**。**強化層の失敗が原点の更新を止めてはならない**（§3.1.2）。

## 7. データ設計

データベースは **音楽グラフ領域**（読み取り専用・月次バッチで再構築）と **アプリケーション領域**（読み書き）の 2 スコープに分ける。前者は `music_v{n}` の連番スキーマで管理し、切り替えはアトミックに行う。

### 7.1 音楽グラフ領域

#### 7.1.0 アーティストの識別子（v3.2 で変更）

v3.1 までは **MBID をそのまま主キー** にしていたが、Apple のカタログを検索対象に含める（FR-01）と、**MusicBrainz に存在しないアーティストが出てくる**ため、主キーを分離した。

| 列 | 意味 |
| --- | --- |
| **`uid`**（uuid, PK） | **DIGGR 内部のアーティスト識別子。必ず存在する** |
| `mbid`（uuid, NULL, UNIQUE） | MusicBrainz にあれば、その MBID |
| `apple_id`（text, NULL, UNIQUE） | Apple Music にあれば、その ID |

**`uid` の発番規則**

| 出所 | `uid` |
| --- | --- |
| MusicBrainz にある | **MBID をそのまま使う** |
| Apple のみ | **Apple ID から生成する決定的な UUIDv5**（DIGGR 専用の名前空間） |

**決定的に生成するのが要である**。月次パイプラインが毎回乱数で ID を振ると、**過去の履歴が今月の DB と繋がらなくなる**。UUIDv5 なら Apple ID が同じ限り常に同じ値になるので、スキーマを何度作り直しても、参照が壊れない。

**MusicBrainz にあるアーティストは MBID をそのまま `uid` にする**ので、v3.1 までに生成されたレコードは **値が 1 つも変わらない**。名称の変更だけで、データ移行は発生しない。

**後から MusicBrainz に登録されたとき**

Apple のみだったアーティストが、後の月に MusicBrainz へ登録されて突合されることがある。**既存の初期 `uid` は消えない**。

| 列 | 扱い |
| --- | --- |
| `merged_into` | uuid, NULL、統合先の `uid` を持つ |
| 表示 | `merged_into` を辿って新しい行を見せる |
| 履歴内の ID | **書き換えない**。`maps.node_uids` は不変（ADR-18） |

**もろもろが後から書き換えない ADR-18 の帰結である**。ノード集合は生成時に確定して二度と変わらないと決めているので、**統合は表示時の転送で吸収する**。初期 `uid` の行は永久に残るが、アーティスト 1 件あたり数百バイトなので問題にならない。

**artists**

| **mbid** | **uuid** | **UNIQUE, NULL** | **MusicBrainz ID。Apple のみのアーティストでは NULL** |

**artist_aliases**（v3.1 で `artists.aliases` から分離）

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| uid | uuid | PK(1) | アーティスト |
| alias | text | PK(2) | 別名・英字表記・愛称・多言語表記 |
| locale | text | NULL | `ja` / `en` など、不明なら NULL |
| source | text | NOT NULL | `musicbrainz`（CC0）/ `apple_feed` |

**`source` で分けているのは、クライアントへ渡す範囲を決めるためである**。検索インデックス（`pg_trgm`）は全件を対象にするので、**オンライン検索では Apple 由来の日本語名が効く**。クライアントへの配布範囲は OI-37 の結果で決まる（§3.5.6 項目 4）。

**artist_similarity**（確定枠用・上位 40 件）

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| src_uid | uuid | PK(1) | 起点アーティスト |
| dst_uid | uuid | PK(2) | 関連アーティスト |
| score | real | NOT NULL | 合成類似度スコア（0.0–1.0） |
| rank | smallint | NOT NULL | src 内での順位（1–40） |
| relation_types | text[] | NOT NULL | `listen` / `collab` / `member` / `influence` / `label` |

確定枠の判定（score ≥ 0.60）に使うのはこのテーブルで、**行が存在するのは `artists.has_graph = true` のアーティストだけ** である。

**artist_pool**（ランダム枠用・41〜650 位）

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| src_uid | uuid | PK | 起点アーティスト |
| pool_uids | uuid[] | NOT NULL | 41〜650 位の `uid` 集合（最大 610 件、順位順） |
| pool_size | smallint | NOT NULL | 実際の格納件数 |

**プールを集合で持つ理由**。ランダム枠はどれを引いてもいい集合なので、スコアも順位も描画に使わない。必要なのは ID だけである。もろもろを行として持つと 200 万 × 610 = **12 億行・約 70GB** になるが、集合で持てば **200 万行・約 20GB** に収まる。

**genres** / **genre_hierarchy** / **artist_genres**

| テーブル | 主な列 | 説明 |
| --- | --- | --- |
| genres | `id`, `name`, `category`, `artist_count` | 正規化済みジャンル。**Discogs の Genre / Style を骨格とする**。`category` は表示色の 8 系統 |
| genre_hierarchy | `parent_id`, `child_id`, `depth` | 最大 3 階層のジャンル木（FR-10） |
| artist_genres | `uid`, `genre_id`, `weight`, `source` | アーティストとジャンルの重み付き関連。**`source` は `discogs` / `wikidata` / `apple`**（§3.2） |

**全アーティストがジャンルを持つ**。Apple のみのアーティストでも、アルバムの `genres` から得られる（§6.2.1）。**もろもろのグラフの無いアーティストでも地図を描ける根拠である**。

**artist_external_links**

| 列名 | 型 | 制約 | 説明 |
| --- | --- | --- | --- |
| uid | uuid | PK(1) | アーティスト |
| service | text | PK(2) | `spotify` / `apple_music` / `youtube_music` |
| external_id | text | NOT NULL | 各サービスのアーティスト ID |
| source | text | NOT NULL | `musicbrainz_url_rel` / `apple_feed_upc` / `apple_feed_direct` |

| **artist_pool（集合で 610 件）** | **約 200 万行 / 約 20GB** |
| genres / artist_genres | 約 3,000 行 / 約 2,000 万行 / 約 1GB |
| **artist_aliases** | **約 600 万行 / 約 0.8GB** |
| artist_external_links | 約 120 万行 / 約 0.2GB |
| **maps（DAU 1,000 で 1 年蓄積した場合）** | **約 300 万行 / 約 8GB** |
| **合計（インデックス込み）** | **約 50〜55GB、FR-01b 有効時は 55〜60GB** |

**FR-01b を有効化すると 80GB SSD の残余は 20GB を割る**。アップデートの一時領域と WAL を考えると余裕は大きくない。**有効化の判断とあわせて CX43（160GB）への移行検討を併せて行う**（技術選定書 §10）。

### 7.4 端末側データ（expo-sqlite）

**v3.1 で新設した層である。** 端末に SQLite を置き、**ユーザーデータの正**と、**サーバー由来データのキャッシュ**を引き受けさせる。実装方式の詳細は技術選定書 §3.5。

#### 7.4.1 どちらが正かを先に決める

| データ | 正 | 端末に置く理由 |
| --- | --- | --- |
| もろもろ（`maps` / `map_nodes`） | **サーバー** | 一度取得すれば不変。二度目以降は通信しない |
| アーティストのメタデータ | **サーバー** | 表示のたびに引き直す必要がない |
| ブックマーク（FR-16） | **端末** | オフラインでも押せることが体験上重要 |
| チェック済み（FR-31） | **端末** | 単一かつ書き込み頻度が高い |
| 聴いた記録（FR-23） | **端末** | 同上 |
| **解放件数の判定（FR-07）** | **サーバー** | **キャッシュしない。毎回サーバーの返す件数に従う** |
| 表示中の閾値（ブックマーク上限・履歴一覧の件数・広告の有無） | サーバー | **直近値を保持しておく**。オフラインでも上限判定ができる必要があるため、復帰時にサーバー値で上書きする |

**この表の最後の行が設計上もっとも重要である**。解放件数の判定をサーバーに集約するのは v2.0 からの方針だが、端末に DB を持たせると **「キャッシュを書き換えればロックが外れるのでは」** という懸念が生まれる。

答えは **端末に届いているのは「その時に権利範囲で受け取った分だけ」だ** ということである。ここで守るべきは **解放件数の判定** であって、権利情報そのものを一切保持しないことではない――ブックマークの上限や履歴一覧の件数は、**オフラインでも判定できないと体験が壊れる**ので直近値を持たせる。**壊れても失うのは上限の緩みだけで、存在しないノードは現れない**。無料ユーザーのレスポンスは 30 件の実データ（70 件のプレースホルダー）`{ locked: true }` のみで名称・ID を含まない、なので `map_nodes` にも 30 行しか入らない。**受け取っていないものはキャッシュできない**。

課金すると差分がサーバーに取りに行く。`map_nodes` に追記する（UC-02 の `expandMap`）。**ペイウォールが穴だらけにならないのは、最初から書き換え可能な形で権利を渡っていないから** である。

#### 7.4.2 持つもの

| テーブル | 内容 |
| --- | --- |
| `maps` | 履歴・ブックマークの実体。`revealed_count`（段階表示の復帰用）と `last_opened_at`（LRU の基準）を持つ |
| `map_nodes` | もろもろ 1 件のノード。`uid` と `idx`（段階表示の順番そのもの） |
| `bookmarks` / `checked` / `listened` | ユーザーの行為。`synced` フラグで遅延アップロードする |
| `artists_cache` | 表示に必要なアーティスト属性。名称・**別名（CC0 由来のみ）**、国・活動年代・人気度・ジャンル・外部リンク ID、**`has_graph`** |
| `artists_fts` | `artists_cache` に対する FTS5 の仮想テーブル。**オフラインでの検索に使う** |

**規模の見積もり**\: もろもろ 60 件 × 最大 100 ノード ＝ 6,000 行、アーティスト実体は重複を除いて数千件。**インデックスと FTS を含めても、数 MB** に収まる見込みである（実測は技術選定書 OI-40）。

**端末の保持上限（60 件）と一覧に見える件数（Free 10 / Pro 全件）は別物である**。前者は技術的な容量管理、後者は課金境界である。**Free ユーザーの端末には 60 件入っている**――課金した瞬間に過去の履歴がすべて現れるのは、この構造によるものであり、買ったら増えたのではなく、**買ったら見えるようになる**。所定の価値が即座に伝わる。

#### 7.4.3 破棄の規約

| 対象 | 規約 |
| --- | --- |
| 履歴 | **端末の保持上限は一律 60 件**（プランによらない）。`last_opened_at` が古いものから削除。**ブックマーク済みは除外する** |
| `artists_cache` | どのもろもろからも参照されなくなった行を週次で掃除 |
| 音楽スキーマが上がったとき | **`artists_cache` のみ破棄する、`maps` は残す** |

**スキーマが上がってもろもろが残るのは、FR-02b の直接の見返りである**。もろもろは `uid` の集合として存在しているので、アーティスト名やジャンルは後から引き直せばよい。**月次更新をまたいでも、一週間前の履歴は同じ地図で開く**――サーバー側の `maps` テーブルと端末側で、同じ保証を同じ理由で成り立っている。

#### 7.4.4 サーバー側 `maps` との関係

**両方持つことを恐れない**。役割が違うので重複ではない。

|  | サーバー側 `maps` | 端末側 `maps` |
| --- | --- | --- |
| 目的 | 全ユーザーの履歴の保存・機種変更・再インストール後の復帰 | その端末での高速・オフライン表示 |
| 保持 | 90 日アクセスなしで削除（ブックマーク済みは永続） | 上限 60 件の LRU |
| 削除したら | 端末側が残っていれば表示は続く | サーバーから引き直す |

**どちらかを消しても体験が破綻しない**ための二重化の答えである。端末が初期化されればサーバーから履歴が戻り、サーバーが 90 日で消しても端末に残っていれば開ける。

**ただし端末にしかないもろもろは作らない**。もろもろ生成は必ずサーバーを通し、`map_id` もサーバーが発番する。ローカルに生成を許すと ID が衝突し、権利判定を回避できてしまう。**端末は常に受け取る側である**。

## 8. API 設計

### 8.0 本章の位置づけ

v1.0 では外部 API を仲介する BFF としてこの層を定義していたが、v2.0 では自社データベースへのクエリを提供する、通常の API サーバである。外部サービスへの中継は行わない。

### 8.1 共通仕様

- ベース URL: `https://api.diggr.app/v1`
- 認証: `Authorization: Bearer <JWT>`。匿名ユーザーにも初回起動時に JWT を発行する
- レスポンス形式: JSON（`Content-Type: application/json; charset=utf-8`）
- エラー形式: `{ "error": { "code": "RATE_LIMITED", "message": "...", "retryAfter": 30 } }`
- レート制限: 認証済みユーザーあたり 60 req/min、超過時は `429`
