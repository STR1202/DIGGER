# 第 I 部　v2.4 からの変更点

v2.4 以降に決まった変更を、決定の理由とともに整理する。
**「なぜ変えたか」を残すのが目的**なので、v2.4 の記述を読んだ人が差分だけ追えるようにしてある。

## 1. 廃止した仕様

| # | 変更 | 理由 | 影響 |
| --- | --- | --- | --- |
| D-1 | **iTunes Search API による試聴プレビューを不採用** | 発注者判断。API 依存と規約リスクを負わない | **FR-06 / FR-24 / SC-17 を削除**。技術選定書 §5.3 の**縮退構成**（`PREVIEW_ENABLED=false`）を正式構成に格上げ（ADR-13）。試聴導線は外部音楽アプリ連携（FR-23）のみ |
| D-2 | **絞り込みの「層」検索（確定層 / ランダム層）を廃止** | 二層構造は地図の見た目で既に表現されている。フィルタに出すと概念が二重になる | 絞り込み条件は **年代 / 関係タイプ / 国** の 3 軸のみ |
| D-3 | **マップ外周で表現する UI を廃止** | 独自表現が学習コストになった。従来の UI 表現に戻す | 外周リング表示を削除。ランダム枠も確定枠と同じ力学レイアウトに統合（ADR-20 を改訂） |
| D-4 | **買い切り課金を廃止** | サブスクリプション 2 種に一本化（ADR-16） | 商品は `pro_monthly` / `pro_yearly` のみ |
| D-5 | **「全体表示」ボタンを廃止** | 常設ボタンとしては使用頻度が低く、下部の操作列を圧迫していた | 機能は**空白部分のダブルタップ**に移設。ボタン列は ジャンル / 絞込 / 中心に戻る の 3 つ |
| D-6 | **Bandcamp 連携を削除** | 発注者判断 | 連携先は Spotify / Apple Music / YouTube Music / **iTunes Store**（新規追加）の 4 種 |

## 2. マップ生成の変更

| # | 変更 | 理由 | 実装 |
| --- | --- | --- | --- |
| M-1 | **最大ノード数 150 → 100** | 実機の描画負荷とラベルの可読性。150 では拡大しても名前が読めない領域が残った | `MAX_NODES = 100`（[map.ts](../packages/core/src/map.ts)） |
| M-2 | **ランダム表示を検索時の任意オプションに変更。既定は OFF** | 既定でランダムだと「同じ検索で結果が変わる」ことが不信につながる。決定的な結果を既定にした | `randomOn`（既定 `false`）。OFF のとき外側は類似度順・人気順の続き |
| M-3 | **引き直し（FR-27）はランダム表示 ON のときだけ有効** | OFF は決定的な並びなので、引き直す対象が存在しない | `canReroll = randomOn && pool.length > slots` |
| M-4 | **ジャンルから掘るモードの表示アーティストを完全ランダム化** | ジャンル内で人気順に固定すると毎回同じ顔ぶれになり、掘る意味がない | ジャンルマップは全ノードを `tier: 'random'` として扱う |
| M-5 | **同じジャンル検索を、関連アーティスト検索と「全く異なる地図」にする** | 同じ顔ぶれが同じ形で並ぶだけでは、軸を変えた意味がない | ①**サブジャンルの島レイアウト**に組み替える ②関連マップに出た顔ぶれ（`knownMbids`）を**後ろに回す** ③島をまたいで round-robin に出し、段階表示で全体の広がりが先に見えるようにした。無料 30 件では**重複 0%** を確認 |
| M-6 | **確定枠からクランプで溢れた候補をプールの先頭に戻す** | 上限で切り捨てると、引き直しの候補から優良な相手が永久に消える | `pool = [...coreAll.slice(core.length), ...低スコア]` |
| M-7 | **関連 ↔ 同ジャンルを往復すると結果がリセットされるバグを修正** | 往復のたびに再生成していた | 履歴から同一 `seedKey` × `viewType` のマップを引き当てて復元する（[map.tsx](../apps/mobile/app/map.tsx) `switchView`） |

# 第 II 部　製品設計

## 6. 目的とスコープ

音楽の関連アーティストを**ネットワークグラフとして掘る**モバイルアプリ。
検索したアーティストを中心に、関係の強さで距離が決まる地図を描き、
そこから次のアーティストへ辿っていく体験を提供する。

**やらないこと**（明確な非スコープ）

- 楽曲の再生・試聴（D-1）。聴く行為は外部音楽アプリに委譲する
- 音源・歌詞・アートワークの保持
- SNS 機能、コメント、フォロー

## 7. 用語

| 用語 | 意味 |
| --- | --- |
| マップ | 1 回の検索で生成される地図。ノード集合そのもので同定する |
| シード | マップの中心。アーティストまたはジャンル |
| 確定枠（core） | 類似度が閾値以上で、常に同じ顔ぶれが出る層 |
| ランダム枠（random） | 確定枠の外側。ランダム表示 ON のときだけ抽選になる |
| ゴースト | 権利範囲外で未解放のノード。数だけを外周に散らして示す |
| 段階表示 | 10 件ずつ開いていく表示方式 |
| 表示タイプ | 「関連アーティスト」か「同じジャンル」か |

# 第 III 部　ドメイン設計

実装は [`packages/core`](../packages/core/src)。**UI を起動せずに仕様を検証できる**ようここに判断を集めている。

## 11. マップの二層構造（FR-02）

```
確定枠 core   類似度 >= 0.60        無料 20 件 / Pro 40 件まで
外側 random   確定枠の続き           合計が 無料 30 件 / Pro 100 件 になるまで
ゴースト      権利範囲外             数だけ外周に散らす
```

| 定数 | 値 | 位置 |
| --- | --- | --- |
| `CORE_THRESHOLD` | 0.60 | `map.ts` |
| `MAX_NODES` | **100** | `map.ts` |
| 無料 | `nodeLimit 30` / `coreCap 20` | `FREE_ENTITLEMENT` |
| Pro | `nodeLimit 100` / `coreCap 40` | `PRO_ENTITLEMENT` |

- 確定枠は**同じシードなら常に同じ顔ぶれ**。引き直しても動かない
- `coreCap` で溢れた候補は捨てず、**プールの先頭に戻す**（M-6）
- ジャンルマップに確定枠は無い（`coreCount = 0`）。全件がランダム枠（M-4）

## 12. ランダム表示と引き直し

| | ランダム表示 OFF（既定） | ON |
| --- | --- | --- |
| 外側の決まり方 | 類似度順・人気順の続き | プールからの抽選 |
| 再現性 | 常に同じ | `randomSeed` から完全再現 |
| 引き直し | **不可**（M-3） | 可。確定枠は動かない |
| `randomSeed` | 0 を保存 | 生成した値を保存 |

**乱数（ADR-19）**: xoshiro128\*\* + 部分 Fisher-Yates。
**重み付けはしない** — 重み付き抽選は「人気のものが出やすい」偏りを生み、掘る目的に反するため。

## 13. 段階表示（FR-28）

- 初期 **10 件**、押すごとに **+10**、長押しで権利範囲まで一括
- **通信は起きない。カメラも動かさない**。描画件数を増やすだけ
- ジャンルマップは島をまたいで round-robin に出すので、**先に全体の広がりが見える**（M-5）

## 14. 表示タイプ（FR-29）

| | 関連アーティスト | 同じジャンル |
| --- | --- | --- |
| 形 | 中心からの放射状。確定枠が内側、続きが外側 | **サブジャンルごとの島** |
| ノード半径 | 類似度が高いほど大きい | 一定 |
| 顔ぶれ | 類似度順 | **関連マップに出た人を後ろに回す** |
| 中心アイコン | 人マーク | **人マーク**（U-5） |
| 力学 | 1 つの力学レイアウトに統合（D-3） | 島の中心へ引き寄せ + 反発 |

どちらも**ラベル幅を見込んだ距離**まで押し広げる（U-2）。

## 15. マップの同定と永続化（FR-02b / ADR-18）

履歴・ブックマーク・引き直しの単位は**マップ**。保存するのは乱数シードではなく
**ノード集合そのもの**（`node_mbids`）。月次更新でプールの中身が変わっても、
一週間前の履歴が**同じ地図で開く**。

- 履歴は最大 60 件（端末）。無料プランは一覧で 10 件まで
- 表示中のマップは永続化しない。履歴から復元する（`partialize`）
- サーバー側は 90 日アクセスの無いマップを削除。ブックマーク済みは残す（R-33）

## 16. 類似度（5 信号）

| 信号 | 重み | 由来 |
| --- | --- | --- |
| 共聴 listen | 0.50 | ListenBrainz の共起集計（開発時はシーン親和で代替） |
| ジャンル genre | 0.20 | ジャンルベクトルのコサイン |
| 共演 collab / メンバー member | 0.15 | MusicBrainz の関係 |
| 影響 influence | 0.10 | Wikidata |
| 同レーベル label | 0.05 | Discogs |

本番では**月次パイプラインが事前計算**し、実行時は DB を引くだけ。
`similarity.ts` は開発用データソース兼、重み変更時の回帰テスト基準として残す。

各データソースの取得方法・ライセンス・レート制限は **§26.1** にまとめた。

## 17. 権利（ADR-16）

- 商品は **サブスクリプション 2 種のみ**（`pro_monthly` / `pro_yearly`）。買い切りは廃止（D-4）
- **権利の正はサーバー**。アプリは表示を先に進めるためだけに購入結果を使う
- 無料の制限: ノード 30 / 確定枠 20 / ブックマーク 10 / 絞り込み不可 / 広告あり

## 23. ラベル配置（U-2）

**画面座標**で配置するため、拡大するほど相対的に空きが出て、隠れていた名前が現れる。

1. 優先順（選択中 → `rank` 昇順）に並べる
2. 各ノードにつき**8 方向の候補位置**を試す
3. 既に置いたラベルおよび中心の予約矩形と衝突しなければ確定
4. どこにも置けなければ**描かない**（重ねて潰し合うより、拡大で読ませる）

倍率 1.2 未満では関連マップのランダム枠ラベルを畳む。**島マップは畳まない。**

ジェスチャ中は再配置せず、確定済みの配置に**差分変換**をかけて追従させる（F-4）。

## 26. 外部データソースと API

DIGGR が触る外部サービスは **性質の異なる 2 種類**がある。混同すると規約と実装の両方を誤る。

| | 月次パイプライン（オフライン） | 実行時（アプリから） |
| --- | --- | --- |
| 何をする | 類似度インデックスを作る | 聴くために外部アプリを開く |
| 対象 | MusicBrainz / ListenBrainz / Discogs / Wikidata | Spotify / Apple Music / YouTube Music / iTunes Store |
| 通信の主体 | AWS Batch（サーバー） | 端末 |
| 認証 | サービスごとのトークン | **不要** |
| 失敗したとき | 前回のスキーマで動き続ける（ブルーグリーン） | OS がブラウザへフォールバック |

**アプリから外部の音楽 API を叩くことは一切ない。** 実行時に触る外部サービスは URL を開く先だけ。

### 26.1 月次パイプラインが読むデータソース

類似度の 5 信号（§16）はここから作る。**いずれも取得はダンプが主で、API は差分確認の用途に限る** —
全件走査を API で行うとレート制限に必ず当たるため。

| サービス | 取るもの | 信号 / 重み | 取り方 | ライセンス |
| --- | --- | --- | --- | --- |
| **MusicBrainz** | アーティストの正体（MBID・名前・国・活動年）と明示的な関係（メンバー / 共演 / レーベル） | `member` `collab` `label` / 0.15・0.05 | 月次フルダンプ `data.metabrainz.org/pub/musicbrainz/data/fullexport/` をローカル展開 | コアデータは **CC0** |
| **ListenBrainz** | 共聴シグナル。同じ利用者が一緒に聴いているアーティストの共起 | `listen` / **0.50（最大）** | リスニングダンプ `data.metabrainz.org/pub/musicbrainz/listenbrainz/` | **CC0** |
| **Discogs** | レーベル所属 | `label` / 0.05 | **月次 XML ダンプ** | ダンプは **CC0** |
| **Wikidata** | 影響関係（`P737 influenced by`） | `influence` / 0.10 | SPARQL エンドポイントまたはダンプ | **CC0** |

**MBID（MusicBrainz Identifier）がアプリ全体の主キー**。`maps.node_mbids`・`bookmarks`・`listened` も
すべて MBID で持つので、他のデータソースは MBID に紐づけてから使う。

#### 各サービスの制約（実装時に必ず確認すること）

| サービス | 制約 |
| --- | --- |
| MusicBrainz | Web Service（`musicbrainz.org/ws/2/`）は **1 リクエスト / 秒**。User-Agent に連絡先を入れることが必須。**商用でライブデータフィード（レプリケーション）を使う場合は MetaBrainz との合意が要る** — DIGGR は有料サブスクリプションを持つため該当しうる |
| ListenBrainz | 公開データの取得に認証は不要。利用者個別のエンドポイントのみトークンが要る |
| Discogs | API（`api.discogs.com`）は認証時 60 req/分、未認証 25 req/分。**API の利用規約は商用利用に制限があるため、CC0 のダンプを使う** |
| Wikidata | SPARQL エンドポイントに同時実行数とタイムアウトの制限がある。大量取得はダンプで行う |

> **現状**: 上記のパイプラインは**未実装**（§32）。いまは `packages/core/src/data/mock.ts`
> （247 アーティスト / 52 ジャンル / 236 関係）を同じインターフェイスで差し込んでいる。
> `similarity.ts` は、パイプラインの重み係数を変えたときの回帰テストの基準として残す。

### 26.2 Spotify ほか音楽サービス — 

外部音楽アプリ連携（FR-23）は、**公開 URL を開くだけ**で実現している。

| サービス | 開く URL |
| --- | --- |
| Spotify | `https://open.spotify.com/search/{artist}` |
| Apple Music | `https://music.apple.com/search?term={artist}` |
| YouTube Music | `https://music.youtube.com/search?q={artist}` |
| iTunes Store | `itmss://itunes.apple.com/search?media=music&term={artist}` |

これを選んだ理由は 4 つある。

1. **API キー・OAuth・SDK が不要**。鍵の保管も更新も要らない
2. **規約同意・アプリ審査・レート制限が無い**
3. **Spotify Developer Terms に触れない。** 同規約は Spotify のデータを使って competing な
   ディスカバリー機能を作ることを禁じているが、**DIGGR は Spotify からデータを一切取っていない**ので
   そもそも適用されない。類似度は MusicBrainz / ListenBrainz / Discogs / Wikidata だけで作る
4. **利用者がそのサービスの契約者でなくても導線が壊れない。** 未インストールなら OS が
   ブラウザかストアへフォールバックする

`itmss://` だけは開けない端末があるため、`Linking.canOpenURL` が false のとき
`https://music.apple.com/search?term=` に落とす（[links.ts](../apps/mobile/src/services/links.ts)）。
iOS は `LSApplicationQueriesSchemes` に 4 スキームを申告済み（§29）。

### 26.3 採用しなかった API

| API | 不採用の理由 |
| --- | --- |
| **iTunes Search API** | **発注者判断で不採用**（D-1）。試聴プレビュー（FR-06 / FR-24 / SC-17）ごと持たない |
| **Spotify Web API** | §26.2 のとおり不要。キー管理と規約リスクを負わない |
| **Last.fm API** | 共聴シグナルは ListenBrainz（CC0）で足りる。Last.fm は商用利用に個別の許諾が要る |
